# Project rules — read before writing code

The architecture contract for this repo is **[`README.md`](./README.md)**. It is
not a getting-started blurb; it defines where every kind of code goes, the data
flow, the auth model, and the recipe for adding a feature. Read it first, then:

- **`src/app/api/README.md`** before adding any Next.js Route Handler.
- **`src/features/users/`** is the reference feature slice — copy it verbatim
  when adding a domain, rather than inventing a new shape.

Non-negotiables (the README explains each):

1. Server Components by default; `'use client'` only at the smallest leaf.
2. `component → hook → service → lib/api/client` — nothing skips a layer, and
   `lib/api/client.ts` is the only browser code that calls `fetch`.
3. TanStack Query owns server state; query keys come from `lib/api/query-keys.ts`.
4. Import through feature barrels using the `@/` alias — ESLint enforces this.
5. Zod validates every boundary: forms, Route Handler bodies, env.
6. No frontend check is authorization — the backend's RBAC is.

Run `npm run check` (typecheck + lint) before considering work complete.

## Get it running — 3 minutes

```bash
node --version                # must be >= 20
cp .env.example .env.local
npm ci                        # `ci` not `install` — you get the verified tree
npm run dev                   # → http://localhost:3000
```

**It runs with no backend and no database.** `NEXT_PUBLIC_AUTH_ENABLED` defaults to
`false`, which signs you in as a preview user so the whole admin UI is browsable
immediately. Set it to `true` the moment you have a real API — the gate code in
`proxy.ts` and `<AuthGate>` is already written and wired.

**Environment files are read at startup.** If you edit `.env.local`, restart the dev
server — a value that "isn't picked up" is almost always this.

### What ships

```
/                    landing
/admin/login         sign-in
/admin/dashboard     stats, activity feed, throughput chart
/admin/users         users table
/admin/activity  /admin/analytics  /admin/reports  /admin/settings
/api/health          liveness + backend reachability
/api/auth/session    login → first-party refresh cookie
/api/proxy/[...path] opt-in transparent passthrough
```

The admin pages are a **working shell with placeholder panels**, not invented data. Fill
them from real queries as you build; do not add fake numbers to make them look finished.

### Two modes — know which one you are in

| | With a backend (Tier 2/3) | Standalone (Tier 1) |
| --- | --- | --- |
| Data comes from | a separate API at `NEXT_PUBLIC_API_BASE_URL` | Route Handlers in `src/app/api/` |
| Delete | `src/lib/db/`, `supabase/` | the sibling `backend/` |

Mixing them gives an app that tries both and does neither.

### Confirm it works

```bash
curl localhost:3000/api/health
```

Always returns **200**, reporting this app and the backend **separately** — so a degraded
API does not make an orchestrator kill this app.

## The stack — exactly this, no substitutions

## The data path — the rule everything else follows

```
component → hook → service → HTTP → backend
                            or
component → hook → service → Route Handler → db
```

**No component calls `fetch` or a database directly.**

```bash
grep -rn "fetch(" src/features src/components src/app | grep -v services/
# → must return nothing
```

## Two API clients — never mix them

| | `src/lib/api/client.ts` | `src/app/api/_lib/backend.ts` |
| --- | --- | --- |
| Runs in | the **browser** | the **server**, Route Handlers only |
| Auth | in-memory token + silent refresh | cookies from the incoming request |
| May hold secrets | never | yes |

## Layout

```
src/
  app/
    (auth)/admin/login/    sign-in
    (app)/admin/*          the admin platform
    api/                   Route Handlers — read src/app/api/README.md first
  features/<f>/            components/ · hooks/ · services/   ← vertical slices
  components/ui/           shadcn primitives

  components/shared/       Section, StatCard, PlaceholderPanel, AuthGate
```

Do not create top-level `controllers/`, `services/` or `types/` folders.

## Rules

- **Server Components are the default.** `"use client"` at the narrowest component that
  needs interactivity, never at the top of a page to silence an error.
- **Never import `@/lib/db/*` or `@/app/api/_lib/*` into a Client Component.**
- **Every screen handles four states**: loading, empty, error, loaded.
- **No placeholder data.** If a screen needs data that does not exist, say so. Do not
  invent numbers, names or rows that look real — `PlaceholderPanel` exists so a
  not-yet-built panel is honestly labelled instead of filled with fiction.
- **Query keys and endpoints come from one place** — `lib/api/query-keys.ts` and
  `lib/api/endpoints.ts`. Never an inline key literal.
- **Route groups are not permission boundaries.** `(app)/admin` is a layout. Anyone can
  call the endpoints behind it with curl. Hiding a control is not authorization.
- **Nothing secret in `NEXT_PUBLIC_*`.** Classify each variable as identifier or secret
  rather than pattern-matching its name.

## Known gotchas

- **`NEXT_PUBLIC_*` is inlined at build time.** Changing one in a hosting dashboard does
  nothing until you redeploy. If production calls `localhost`, this is why.
- **`NEXT_PUBLIC_AUTH_ENABLED=false` means every route is publicly reachable** and you are
  signed in as a preview user. Do not ship to real users in that state.
- **No trailing slash on `NEXT_PUBLIC_API_BASE_URL`** — one double-slashes every path.
- **`src/lib/db/` is excluded from typecheck** in `tsconfig.json`; three activation steps
  are at the top of that file.
- **`cookies()`, `headers()` and `params` are async in Next 16.** `await` them.
- **`SESSION_COOKIE_NAME` must match the backend exactly**, or refresh silently fails.
